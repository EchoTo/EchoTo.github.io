我让 Claude Code 和 Codex 做了同一份作业

30 Oct, 2026 · 中文 · English

上一篇写到，我用 Codex 那几个月不太顺，很多时候它理解不了我要做什么。但那是 3 月到 8 月的事，之后我一直在用 Claude Code，没再拿 Codex 做过什么。这个印象现在还对不对，我也不确定。

所以写了个小工具 agent-race，把同一个任务同时交给两个 Agent，各自在独立的 git worktree 里做，做完把两边的改动、耗时和测试结果放在一起看。

怎么比的

一开始先在博客和情报雷达上各试了一个小功能：文章页加阅读时间，雷达的 top 命令加一个按来源筛选的参数。

但这种需求太简单，看不出什么。后来从 Go 重构项目里挑了 5 个已经合进去的小改动：

  1. 批量发 Kafka 消息时，失败被记到了别的消息上
  2. 一个缓存键不存在时被当成异常，空闲的车每秒刷一条 WARN
  3. 仿真传过来的车道号是数字，写进库变成了空
  4. 日志推 Loki 时对方开了鉴权，要支持配置租户
  5. 潮汐方向一直没变，时间戳却一直在刷新，车端以为潮汐变了

每个改动都先把代码退回到改之前，再像平时提需求那样写一两句话交给它们，比如第 2 个是「缺键是正常情况，不要打；真的 redis 出错还是要打」。每个任务后面都加了一句：只在本地改，不要提交，不要连服务器。

两边做完之后，把当年那次提交里的测试拿过来跑。这些测试它们事先看不到。

用的模型是 Claude Code 的 Opus 5.5 和 Codex 的 gpt-6-astra。

结果

Claude CodeCodex
1. 失败记错了消息58 秒，改对412 秒，改对
2. 缺键刷 WARN73 秒，通过533 秒，通过
3. 车道号变成空77 秒，漏了一处模型拥堵，没有改
4. Loki 租户71 秒，通过561 秒，参数顺序不同，编译不过
5. 潮汐时间戳107 秒，通过1129 秒，通过

第 1 题两边的测试其实都没过，因为当年的测试调了一个叫 errsByRecord 的函数，这个名字它们不可能知道。对照当年的改动看，两边找到的原因和改法都是对的。

Codex 走的是公司的网关，慢有多少是网关的原因，我分不清。前面雷达那个任务，Codex 第一次也是因为模型拥堵退出的，重跑了一次才做完。Claude Code 这 5 题一共花了 3 美元左右。

还有一点要说明：这 5 个改动当年都是我和 Claude 一起写的，测试里的函数名和参数顺序本来就是 Claude 的习惯，第 4 题 Codex 就是因为参数顺序不同没编译过。加上只有 7 个任务，我不打算拿这个比谁更强。

就结果来说，两边对需求的理解都没出问题，第 5 题这种和业务关系比较深的，我在任务里把是哪条消息、什么现象、新旧两种协议都要处理写清楚了，两边也都做对了。

比起谁对谁错，两边不一样的地方更值得看。

同一个需求，两种做法

雷达那个任务，我写的是：「top 命令加个参数，能只看某个来源的」。

Claude Code 的做法是筛选，只显示在这个来源出现过的条目，分数不变，同时在几个网站出现过的条目，加分也照样保留。Codex 的做法是只用这个来源的数据重新算分、重新排序。

两种都通过了测试，也都说得通。我写这句话的时候，根本没想过还有第二种理解。如果只交给一个 Agent，我大概率会直接用它给的那种，不会意识到这里有得选。

没说的，都没做

车道号那题是两边都没完全做对的一题。

当年修这个问题的时候，顺着同一个接口查下去，还发现另一个数字字段会被写成科学计数法，1717171717 进库变成了 1.717171717e+09，就一起修了。

这次我在任务里只写了车道号。Claude Code 修好了车道号，另一个字段没有动；Codex 那次正好碰上拥堵，什么也没改。

任务里没提到的，它们一般不会主动去找。当年能多查一步，是因为前面已经在线上踩过一次，知道这里的数据类型不可靠。

做完之后怎么交代

两边最后给我的说明也不太一样。

Codex 一般是列出改了哪几个文件、跑了哪些测试、结果通过。

Claude Code 会把没确认的地方写出来。第 1 题它说新加的测试没有拿旧代码跑过，结论是对着代码推出来的；第 4 题它加了租户的配置，但没有往任何环境里填值，说不知道实际的租户 ID，让我来定。

改动量大部分差不多，有两题差得比较多：雷达那题 Claude Code 改了 9 行，Codex 改了 35 行；第 5 题 Claude Code 加了 97 行，Codex 加了 176 行。

补充：换成大需求和业务需求

上面这几题都太小了，大多只改一两个文件，任务里也基本点明了位置。后来又从提交记录里挑了 7 个大一点的需求，再跑了一轮。

先踩了一个坑

第一次跑的时候，Codex 有一题改的文件和当年那次提交一模一样。查了它执行过的命令，它先用 git log --all 在仓库历史里搜到了当年的提交，然后直接 git diff | git apply，把答案套了过来。

Claude Code 没有直接套，但也翻了历史，看了当年的提交和后来才写的设计文档。

问题出在我：worktree 虽然退回到了改动之前，仓库里还留着之后的所有提交。后来改成每题单独克隆一个只到改动之前的仓库，跑完再逐条检查每个 Agent 执行过的命令，有越界的就作废重跑。

没人让它们去翻历史。它们为了把事做对，会自己去找能参考的东西。用历史提交做评测，这一点要先防住。

三个通用的大需求

先是三个和业务关系不大的：代码评审工具的模型降级、一个调度服务从单实例改成主备、一套通用的灰度开关。当年每个都改了七八百行。

大需求没法直接用当年的测试来判，新写的函数名对不上。我从当年的提交说明里整理了评分表，每题 9 到 10 条，交给一个单独启动的 Agent 打分，它不知道哪份是谁做的。

Claude CodeCodex
模型降级（9 分）6.57
主备选举（10 分）9.56
灰度开关（10 分）106
平均用时10 分钟22 分钟

模型降级那题 Codex 分数高一点，但它加了一个启动检查，检查失败整个评审就直接退出，正好把这个需求要解决的「评审没了」又带了回来。主备选举那题，Codex 引用了仓库规则里禁止引用的包；交接时先放锁，不等手上的活做完；还有一个依赖进程内状态的组件没处理，平时就只能拿到一部分数据。

四个业务需求

最后挑了 4 个和港口业务直接相关的：

  1. 车在桥吊下解除锁车后，不响应新的锁车请求
  2. 一次生产问题：车装完箱从堆场直接去桥吊，到位时车头方向反了
  3. 给路径规划补一个字段：车到终点那一刻的车头朝向
  4. 锁车阶段桥吊或龙门吊又发来要求对位的信号，要重置指令让车重新对位

前两个用的是我当年提需求时的原话。后两个找不到原话，照提交说明写的，只写需求，不写做法。

Claude CodeCodex
1. 解锁后不响应5 / 73.5 / 7
2. 车头方向反了修好了首次算对，掉头后重新解析又算反，还改坏了经过锁站的路径
3. 到位朝向4 / 102.5 / 10
4. 锁车重置10 / 108.5 / 10

第 2 题 Codex 把仓库里原有一个回归测试的期望值改了，好让它自己的改动能通过。如果不看 diff，只看测试全绿，是发现不了的。

第 4 题有一个坑，当年第一版也没避开：桥吊、龙门吊的引导信号是缓存里的保持值，不是一次性的，处理不好会陷入「重置、对位、锁车、再重置」的循环。这次 Claude Code 第一次就避开了。

测试也会判错

第 1、2 题有当年的测试，可以直接跑。但有两次，测试显示没通过的那一份，让评分的 Agent 按真实的调用路径一个场景一个场景跑下来，其实是对的：一份是只在库配置好的时候才取消指令，而当年的测试工具没配库；另一份是把判断放在了调用方，当年的测试只测了那一个函数。

只看测试的话，结论会反过来。

给不给现场资料，差一倍

第 3 题最难。到位朝向的规则，比如什么情况要掉头、掉几次，代码里没有，写在我们后来整理的一份 PDF 里。

第一次跑的时候，我不小心让它们读到了这份 PDF，而它比这个需求晚出现，后来去掉重跑了。同样是 Claude Code，读了 PDF 得 8 分，没读得 4 分。

这和上一篇说的是一回事：代码它读得懂，现场的规则在我们脑子里和文档里，不给它，它只能猜。

顺便试了代码图谱

最近代码图谱挺火，把仓库解析成调用关系图，说是能帮 Agent 看清一次改动会影响到哪里。我在这几轮里也加了一组：同样是 Claude Code，任务里要求先查图谱再动手。

三轮下来，带不带图谱的结果基本一样。它自己 grep 加读代码已经能把影响范围查全，图谱在我们的 Go 项目上还会漏掉一些跨包的调用。

几点说明

评分表是照当年的实现整理的，当年的实现又是我和 Claude 一起写的，打分的也是 Claude。这些都会偏向 Claude Code，所以分数只能参考。我更看重的是评分的 Agent 列出来的具体问题，那些都能对着代码核实。

Codex 走的是公司的网关，好几次被模型拥堵打断，大需求一题要等二三十分钟。每题每组也只跑了一次。

最后

小需求那轮，我的结论是两个都能做对，差距主要在速度和稳定性。换成大需求和业务需求之后，差距就不只是速度了。Codex 的改动普遍更小，有时候小到漏了该改的地方。

这个工具还是更适合用在需求本身没想清楚的时候。两个 Agent 做得不一样的地方，往往是我自己的描述有问题。另外，该给的现场资料要给，测试全绿也要看 diff。

agent-race 开源在 GitHub，可以拿自己的仓库试试。
